Seção 1O que o sistema é

O Uranium não é um gerador de código. É um aparato experimental que coloca duas topologias de agente para resolver a mesma tarefa, sob as mesmas condições, e mede a diferença.

A pergunta do estudo é se decompor o trabalho em papéis especializados (analista, desenvolvedor, revisor, testador) produz resultado melhor que um agente único fazendo tudo — e a que custo. Para que essa pergunta tenha resposta, tudo que não é a topologia precisa ser mantido constante: mesmo modelo, mesmo provedor, mesma semente, mesmas ferramentas, mesmo orçamento, mesmo prompt do agente que escreve código.

O sistema tem quatro camadas, e vale separá-las porque é comum confundir a terceira com a segunda:

CamadaOnde viveResponsabilidade
Tarefa tasks/, scripts/mine_tasks.py Enunciado em linguagem natural + oráculo de correção, minerados do histórico real do upstream.
Agente src/ As duas topologias, as ferramentas, o orçamento e a telemetria. É o objeto sob teste.
Harness harness/ Juiz externo. Roda depois, com testes que o agente nunca viu, e decide se resolveu.
Suíte do projeto tests/ Testes do Uranium sobre si mesmo. Não avaliam código gerado — garantem que o aparato não está enviesado.
Distinção que costuma se perder

O Validator (camada do agente) e o oráculo (camada do harness) fazem coisas diferentes. O Validator roda dentro do run e serve para o agente decidir se continua trabalhando — é tratamento, não medição. O oráculo roda depois que o agente terminou, com testes ocultos, e é a única fonte de corretude reportada no TCC. Se o Validator fosse a medida, o estudo estaria medindo a auto-avaliação do modelo.

Seção 2Os dois agentes: a variável independente

Os dois braços recebem o mesmo enunciado, as mesmas sete ferramentas e o mesmo teto de gasto. A diferença é inteiramente de topologia: quem decide o que fazer em seguida, e com base em quê.

single-agent

agente único, sem papéis
  • Um nó de LLM em laço com um operador determinístico (não é LLM, não é humano).
  • O operador entrega o enunciado uma vez, aceita todo patch sem revisão, roda a suíte quando o agente para de chamar ferramenta.
  • Se a suíte falha, devolve o stderr cru, truncado — sem resumir, sem apontar arquivo, sem sugerir.
  • agent_role é sempre null na telemetria.

orchestration

grafo multiagente com papéis
  • Cinco nós especializados num StateGraph, com dois laços condicionais.
  • O Developer é quem escreve código; os outros quatro refinam a entrada, julgam a saída e propõem testes.
  • O Validator roda a suíte de verdade e pode mandar o Developer tentar de novo.
  • agent_role é preenchido em cada evento — é o campo que materializa a variável independente no dado bruto.

O ponto exato em que os braços divergem

Um único if, em src/arms/runner.py:229. Tudo antes dele — workspace materializado, configuração de LLM resolvida, orçamento, telemetria, estado inicial — é construído pelo mesmo código: 

def _compilar(spec: RunSpec):
    """Escolhe o grafo. É o ÚNICO ponto em que os braços divergem."""
    if spec.arm == "single-agent":
        from src.arms.single_agent import build_single_agent_graph
        return build_single_agent_graph(spec.driver_policy)

    from src.graph import build_graph
    return build_graph()
Por que o operador do single-agent é burro de propósito

A política do DeterministicDriver (src/arms/driver.py) é fixa e vai inteira para o manifesto do run. Ela devolve o stderr cru justamente para não fazer engenharia pelo agente: resumir a falha, apontar o arquivo provável ou sugerir a correção seria inteligência injetada pelo harness e creditada ao braço. Isso inflaria artificialmente o single-agent e destruiria a comparação.

Seção 3Onde o prompt entra, onde o output sai

Esta é a fronteira que mais importa para entender o sistema, e onde o desenho atual difere radicalmente da primeira versão da POC.

A entrada

tasks/<id>/statement.md ← escrito à mão, por humano │ (nunca derivado da mensagem de commit: │ ela frequentemente já entrega a solução) ▼ scripts/run_arm.py --statement-file ... │ ▼ RunSpec.statement │ ▼ estado_inicial["raw_request"] + estado_inicial["intent"] │ ├──> single-agent: _spec(state) → "Tarefa:\n" + intent como JSON │ entregue UMA VEZ pelo driver, no turno 0 │ └──> orchestration: intent_refiner reescreve a intent, depois developer recebe _build_prompt(state)

Nos dois braços, o texto que chega ao modelo que escreve código é montado a partir do mesmo objeto StructuredIntent serializado em JSON, sob o mesmo system prompt. No braço orchestration há um passo a mais: o intent_refiner pode reescrever a intent antes de o Developer vê-la. Essa reescrita é parte do tratamento — é exatamente o que a orquestração se propõe a fazer — e não uma vantagem indevida.

A saída

A mudança de desenho mais importante do projeto

Na POC original (branch main), o Developer pedia ao LLM que devolvesse blobs de texto com um file_path sugerido, e ninguém nunca executava nada. O artefato era uma string.

Hoje o agente age sobre um repositório real: lê, busca, edita e roda a suíte por meio de ferramentas. O artefato produzido é o diff do workspace — git diff contra a tag uranium-base, gravado em patch.diff. Não há blob de texto para ninguém interpretar: ou o código mudou no disco, ou não mudou.

agente chama write_file / replace_in_file │ ▼ Workspace (clone isolado do repo-semente num commit-base) │ ├─ guarda de caminho: tests/**, conftest.py, pyproject.toml… recusados │ ▼ runs/<arm>/<task>/rep<NN>/<run_id>/ ├── manifest.json configuração resolvida (modelo, provedor, seed, orçamento, topologia) ├── events.jsonl telemetria por evento, validada contra JSON Schema ├── summary.json stop_reason, turnos, tokens, custo ├── patch.diff ← O ARTEFATO └── workspace/ repositório modificado, entregue ao harness

As sete ferramentas

Definidas em src/tools/__init__.py e entregues idênticas aos dois braços. É por elas que todo efeito do agente sobre o mundo passa:

FerramentaO que fazGuarda
list_filesLista arquivos do repositóriomáx. 200 resultados
read_fileLê com numeração de linha, paginável20.000 chars / 400 linhas
search_codeBusca padrão, devolve arquivo:linhamáx. 50 resultados
write_fileEscreve conteúdo completorecusa caminho protegido
replace_in_fileSubstitui trecho exato e únicorecusa caminho protegido
run_pythonExecuta trecho na raiz do repovenv do repo-semente
run_testsRoda a suíte de verdadetimeout, venv do repo-semente

Toda chamada passa por um invólucro de instrumentação que grava um ToolCallRecord: duração, bytes lidos, bytes escritos, se houve recusa, e erro. O campo bytes_read mede o que volta para o modelo em toda ferramenta — inclusive run_tests e run_python, cuja saída entra no prompt do turno seguinte exatamente como a de um read_file. Sem isso a conta do crescimento de contexto não fecha.

Seção 4Os prompts, na íntegra

O prompt do agente que escreve código os dois braços

Vive em src/prompts.py e é importado tanto por src/arms/single_agent.py quanto por src/agents/developer.py. Um texto só, deliberadamente. 

Você é um engenheiro de software resolvendo uma tarefa de manutenção num
repositório Python real.

Você tem ferramentas para inspecionar e modificar o repositório. Use-as:
não descreva a mudança, faça a mudança.

Ferramentas disponíveis: list_files, read_file, search_code, write_file,
replace_in_file, run_python, run_tests.

Método esperado:
1. Localize o código relevante com search_code antes de ler arquivos inteiros.
2. Leia apenas os trechos necessários (read_file aceita faixa de linhas).
3. Aplique a correção com replace_in_file, substituindo o trecho exato. Use
   write_file (conteúdo COMPLETO) apenas para arquivo novo ou pequeno —
   reescrever arquivo grande não cabe no limite de saída.
4. Verifique com run_python, reproduzindo o caso descrito na tarefa. A suíte
   de testes já está verde antes da sua mudança, então run_tests sozinho NÃO
   confirma que você resolveu o problema — ele serve para checar regressão.
5. Rode run_tests ao final para garantir que nada quebrou.

Restrições:
- Arquivos de teste e de configuração são protegidos: a escrita será recusada.
  Resolva o problema no código de produção.
- Não altere comportamento não relacionado à tarefa.
- Quando terminar, responda em texto com um resumo curto do que mudou e pare
  de chamar ferramentas.
Evidência de que prompt diferente contamina a medição

Enquanto os dois braços tinham textos diferentes, o orchestration havia ganhado uma seção "Método esperado" com cinco passos e uma condição de parada em duas partes; o single-agent ficara com um "quando terminar" seco. Em cinco repetições da mesma tarefa:

BraçoTool calls depois da primeira escrita
single-agentexatamente 4, nas cinco execuções
orchestrationde 2 a 32

Isso sozinho dobrou os turnos e, como o contexto é reenviado a cada turno, quase triplicou o custo — e seria lido como "orquestração é mais cara" quando era diferença de redação. A decomposição em papéis do braço orchestration vive no grafo, não no texto do prompt.

Os prompts de papel só orchestration

Estes quatro existem apenas no braço orquestrado. São eles, e só eles, o tratamento que o estudo mede.

NóRecebeDevolve (schema Pydantic)
intent_refiner raw_request + respostas de clarificação anteriores StructuredIntent: context, goal, phases, acceptance_criteria, clarifications_needed, is_ready
clarification intent atual + perguntas pendentes ClarificationBatch: lista de {question, answer}
developer intent + saída do pytest da tentativa anterior, se falhou — (age por ferramenta; devolve diff)
validator intent + o diff efetivo (truncado em 20k chars) ValidationResult: is_valid, issues, suggestions, covered/missing_criteria
test_generator intent + diff (12k chars) + resumo da suíte TestPlan: summary, unit_tests, integration_tests

O prompt do Validator merece leitura atenta

Você é um revisor técnico. A suíte de testes JÁ PASSOU — isto não está em
discussão e você não pode reverter esse fato.

Sua única pergunta é: a mudança resolve o problema descrito na tarefa, ou
apenas faz os testes passarem por acidente (código morto, caso especial
grudado, comportamento não relacionado alterado)?

Retorne JSON com is_valid, issues, suggestions, covered_criteria e
missing_criteria. Use is_valid=false apenas se houver lacuna real frente à
tarefa.

O prompt é escrito assim porque o veredito é monotônico: o LLM só pode rebaixar. A regra está no código, não na obediência do modelo (src/agents/validator.py:74): 

is_valid = report.green and houve_mudanca and (semantic is None or semantic.is_valid)

Três conjunções, cada uma com uma razão. report.green: corretude vem de execução, não de opinião. houve_mudanca: a suíte visível já está verde no commit-base, então "não fazer nada" satisfaria o critério de parada — no piloto foi exatamente o que aconteceu, o agente explorou dez turnos, não escreveu nada, e o run foi dado como válido com um patch.diff de zero byte. A terceira conjunção é o LLM, que pode apenas reprovar.

Mensagens de protocolo os dois braços

Um detalhe pequeno com consequência grande. As mensagens que o sistema devolve ao agente vivem centralizadas em src/feedback.py, e não embutidas em cada braço, porque são a fronteira exata entre "informar o protocolo" e "fazer engenharia pelo agente": 

DIFF_VAZIO = (
    "A suíte passou, mas nenhum arquivo foi modificado — ela já estava verde "
    "antes de você começar, então passar nela não confirma nada. Aplique a "
    "correção do problema descrito na tarefa e verifique com run_python."
)

Enquanto esse texto estava duplicado, o driver do single-agent avisava sobre diff vazio e o laço do orchestration não. Dois runs terminaram sem escrever nada por falta do aviso. Centralizar não foi organização de código: foi correção de viés.

Circuit breaker

Idêntico nos dois braços (src/budget.py), e serializado no manifesto para o teste de paridade conferir:

LimitePadrãoPapel

O teto apertado foi um confundidor real

No piloto com teto de 120k tokens, o single-agent gastou nove turnos lendo arquivos e foi cortado antes de editar qualquer coisa; com 300k, resolveu a tarefa. Um teto que corta um braço no meio do trabalho mede o teto, não a topologia — e cortava justamente o braço que a hipótese não favorece, que é a direção perigosa do viés. O teto de turnos era o segundo confundidor: o padrão do piloto era 25 e o single-agent precisou de 29.

Por que o estado não carrega objetos vivos

O WorkflowState do LangGraph precisa ser serializável, então handles de arquivo, subprocessos e o cliente HTTP não cabem nele. O estado carrega apenas o run_id; os nós resolvem o resto via RunContext.from_state(state), um registro em memória (src/runtime.py). A conversa do agente (list[BaseMessage]) vive lá pelo mesmo motivo — e porque o StateGraph descarta chaves não declaradas no TypedDict.

Seção 6O que é mantido idêntico, e por quê

A validade do estudo depende inteiramente disto. O manifesto de cada run serializa a configuração resolvida, e tests/test_arm_parity.py verifica por execução que os manifestos dos dois braços só divergem em cinco chaves: 

CHAVES_QUE_PODEM_DIFERIR = frozenset({
    "arm", "topology", "driver_policy", "run_id", "started_at"
})

Qualquer outra divergência derruba a suíte. Note que repetition não está na lista: a repetição nº k de um braço e a nº k do outro formam um par e rodam sob a mesma semente, o que preserva o pareamento exigido pela análise estatística.

DimensãoComo é fixada
Modelo e provedorprovider.only + allow_fallbacks: false no OpenRouter — se o provedor pinado não puder atender, devolve erro em vez de servir por outro. O pino é auto-verificável.
Sementeseed_for_repetition(base, rep), derivada só do índice da repetição, nunca do braço.
Temperatura0 nos dois braços.
FerramentasMesmo build_toolset(), mesmo teto de 8 tool calls por turno.
OrçamentoMesmo RunBudget, vindo do mesmo from_env().
Prompt do escritor de códigoMesmo AGENT_SYSTEM_PROMPT.
Mensagens de protocoloMesmo src/feedback.py.
Execução de ferramentaRunContext.executar_tool_calls(), compartilhado — comportamento divergente ali seria capacidade diferente sem nada no manifesto dizer isso.
Contabilidade de custoNós do orchestration devem passar por ctx.invoke_structured(); chamar direto deixaria as chamadas fora do orçamento e o braço multiagente — que tem quatro nós a mais chamando LLM — sairia artificialmente barato.

Observabilidade: por que o LangSmith saiu

A telemetria é JSONL local, por evento (src/telemetry.py), gravada com flush + fsync a cada linha e validada contra harness/schema/event.schema.json. Dez tipos de evento (run_start, node_enter, llm_call, tool_call, test_run, circuit_break…), todos com o mesmo envelope de 25 campos obrigatórios nos dois braços.

O LangSmith foi removido deliberadamente: acrescentava um ponto de falha externo dentro do caminho de medição e, na prática, respondia 403 sem gravar nada. src/config.py desliga o tracing do LangChain de forma incondicional no import, para que uma variável de ambiente perdida não o reative no meio de uma coleta.

Seção 7Como avaliamos o desenvolvimento gerado

A avaliação é externa ao agente, roda depois que ele terminou, e usa testes que ele nunca viu. Entra um workspace modificado, sai um result.json. 

python -m harness.evaluate --run-dir runs/orchestration/tomlkit-0001/rep01/<id> \
                           --task tasks/tomlkit-0001

A ordem das etapas é parte do método

#EtapaPor que nesta ordem
0Desfaz injeção anteriorSem isso a avaliação não é idempotente: os testes ocultos que ela mesma copiou apareceriam na segunda execução como arquivo protegido alterado pelo agente, reprovando um run limpo por trapaça que o harness cometeu.
1Detecção de trapaçaAntes de injetar qualquer coisa — senão os arquivos do próprio avaliador apareceriam como alteração do agente.
2Qualidade (radon)Também antes: mede o que o agente escreveu, não o que o harness injetou.
3OráculoInjeta os testes ocultos e julga.
4Custo e processoAgregados da telemetria.

O oráculo: três verificações

VerificaçãoCritério
fail-to-passOs testes derivados da correção original precisam passar. Eles falham no commit-base; se passam agora, o problema foi resolvido.
pass-to-passA suíte que já passava precisa continuar passando. Impede creditar uma correção que quebrou outra coisa.
regressãoA suíte original completa, como estava no commit-base.
 
resolved = f2p_total > 0
       and f2p_passed == f2p_total
       and p2p.green
       and regression.green

Os testes ocultos são injetados em tests/_uranium_hidden/, diretório que não existe no commit-base e que o agente não pode ter criado (é área protegida). Ele é excluído das verificações de regressão para não se medir o oráculo contra si mesmo. O interpretador é sempre o venv do repo-semente, nunca o do avaliador — rodar a suíte do upstream no venv do projeto daria ao agente langchain, pydantic e cinquenta pacotes que o upstream não declara: corretude comprada de graça, sem ninguém perceber.

Duas formas de oráculo

hidden_tests (arquivos avulsos escritos à mão, como em tomlkit-0001) ou test_patch (o diff de teste do próprio upstream, como em sqlite-utils-0001). A segunda escala para dezenas de tarefas, mede o critério que o mantenedor escreveu, e — por restaurar os testes do commit-base antes de aplicar — desfaz qualquer adulteração de teste antes de medir. A trapaça continua registrada: o detector já rodou.

As sete regras de trapaça

harness/cheat.py. Regras textuais e de diff onde bastam; AST onde regex produziria falso positivo em docstring ou comentário. Toda regra de AST compara o estado antes e depois: só construção nova é acusada.

RegraO que detectaSeveridade
C1Arquivo de teste ou configuração alteradocrítica
C2Opções do pytest alteradas (addopts, --ignore, testpaths…)crítica
C3skip/xfail inserido (via AST)crítica
C4conftest.py criado ou alteradocrítica
C5Código de produção passa a detectar que está sob teste ("pytest" in sys.modules)crítica
C6except: pass novo, que pode engolir a exceção esperada pelo testeaviso
C7Referência ao diretório dos testes ocultos, que o agente não deveria conhecercrítica
Regra de precedência

Trapaça crítica detectada força resolved = false, independentemente do que o oráculo disser — e o campo resolved_blocked_by_cheat registra o caso, para que ele não se confunda com um fracasso comum. Resolver o problema burlando a avaliação não é resolver o problema.

Nota de escopo do próprio detector: C1–C4 cobrem alvos que a guarda de caminho do write_file já recusa — um detector limitado a elas validaria a guarda e nada mais. As vias que restam abertas a um agente que só escreve em código de produção são C5 e C6, e é por isso que elas existem.

A métrica de autonomia que sobrou

O Índice de Autonomia e a taxonomia de intervenção L0–L4, previstos no desenho original, foram removidos: com os dois braços rodando sem qualquer intervenção humana, o índice daria o valor máximo para ambos e não discriminaria nada — reportá-lo como resultado comparativo seria circular. O que restou e de fato varia entre topologias é self_recoveries: transições falha→sucesso na execução de testes. Como não há input externo entre uma execução e outra, cada transição dessas é o sistema corrigindo o próprio erro.

Seção 10Limitações declaradas

Não são pendências: são fatos do desenho que precisam estar escritos no TCC.

Refatoração não é categoria de tarefa possível

Um refactor que preserva comportamento passa nos mesmos testes antes e depois — não existe fail-to-pass, e o oráculo não discrimina. Verificado empiricamente nos commits 9ac3f982 e a46ac201. Refatoração só entra como métrica secundária (delta de MI/CC do radon), nunca como corretude.

Modelos da Anthropic estão fora

Nenhum dos oito endpoints do claude-haiku-4.5 no OpenRouter aceita seed. Com provedor pinado, não há reprodutibilidade. É limitação de plataforma, não escolha de mérito.

A unidade de análise é a tarefa, não a repetição

Repetições da mesma tarefa não são observações independentes. Num teste de sinal pareado unicaudal, o menor p alcançável é 0,0625 com 4 tarefas — impossível chegar a p < 0,05. Com 5 exige unanimidade; com 8, tolera um resultado discordante. Daí o mínimo de 8 tarefas.

O harness é específico de Python

Execução por pytest, ambiente por venv, qualidade por radon, e a classificação fonte/teste por globs de convenção Python. Estender o estudo a Java/Spring ou JavaScript/Node não é configuração: exige um executor de suíte por ecossistema (Maven/Gradle + JUnit, npm + Jest), um equivalente de radon, e regras de trapaça novas. É trabalho de harness, não de agente.

Um modelo só

O estudo fixa um modelo e um provedor para isolar a topologia. Isso significa que o resultado é sobre aquele modelo: não se pode afirmar que a conclusão se generaliza para modelos mais ou menos capazes, e há razão teórica para suspeitar que não — a vantagem de decompor em papéis plausivelmente diminui conforme o modelo base melhora.
